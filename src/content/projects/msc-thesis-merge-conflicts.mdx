## Overview

My thesis sits inside the University of Bern Software Engineering Group's merge conflict research
programme. The team predicts *how* a merge conflict will be resolved (take ours, take theirs,
combine, rewrite) from features of the conflicting code chunks and their history.

The question I own: **which of those features are worth computing?** Text embeddings from a
language model are the most expensive inputs. If a compact set of features, or cheap text-similarity
measures, keep most of the accuracy, the classifier becomes far cheaper to train and run.

## What I built

- **One package, one CLI.** Every experiment is a config file run by the same command, with no
  notebooks or one-off scripts. Each result folder traces back to a config and a commit.
- **Exact parity with the team's code.** The evaluation loop mirrors the team runner fold for fold
  and adds one hook: feature selection on the training split, after cleaning and before fitting.
  A test asserts that with all features the metrics equal the team's exactly.
- **Leakage guards as tests.** Folds are grouped by merge, and by project, language or time as the
  protocol requires. Selection never sees test data.
- **Cluster runs with guard rails.** Experiments run on the UBELIX HPC cluster via Slurm, reached
  through an Azure jump host; the push script refuses uncommitted code, so every run names a commit.

## Status

The reproduction gate passed. Feature-family selection, embedding-input ablations and compact-set
