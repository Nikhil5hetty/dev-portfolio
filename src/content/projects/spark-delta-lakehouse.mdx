## Overview

This project is the pattern I reach for when streaming data has to stay correct after replays and
backfills. It separates transport (Kafka) from history (an append-only `event_lake` Delta table),
then builds the medallion layers from that history.

## Data flow

1. Source applications publish events to topic-specific Kafka topics, defined in `schema/catalog.yml`.
2. A Spark Structured Streaming job writes every raw event, plus ingestion metadata, to `event_lake`.
   The table is never updated in place.
3. **Bronze** keeps the newest valid event per topic and record key.
4. **Silver** standardizes types and text fields, enforces business rules and drops invalid rows.
5. **Gold** publishes serving-ready aggregates by event topic and product type.

## Implementation details

- `deduplicate_bronze_frame()` ranks rows with a window partitioned by the dedup key and ordered by
  recency, keeping `row_number() == 1`, so rebuilding Bronze from the same history always produces
  the same result.
- The same ordering rule exists as pure Python (`select_latest_records()`), unit-tested with pytest
  for newest-event-version and replay-time tie-breaking.
- A CLI (`seed-topic-samples`, `stream-event-lake`, `rebuild-all`) runs the full flow locally against
  the Docker Kafka stack.

## Why an event lake

Kafka retention is short. That is fine for moving data, but not for history. With `event_lake` as
the durable raw layer, Bronze can be rebuilt when logic changes or a downstream table is corrupted,
without asking source teams to re-send data.
